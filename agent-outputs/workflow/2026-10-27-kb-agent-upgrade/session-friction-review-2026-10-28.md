# lark-cli 新能力实施·插件摩擦复盘

## 0. 会话概况（为什么这次复盘有代表性）

一句话任务全貌：基于三份 fuxi 设计文档（U22-U51），以共享树多 Agent 并行方式实施 22 个切片（写回历史安全网/白板 SVG 通路/引用图/反向发布/移出链/评论溯源/装箱等），经 diting 三轮收口审核（10 Major 全闭合）后分七批提交，最终基线 server 1702 + 前端 351 + 三段 typecheck 全绿、工作区零残留。

对插件的压测强度：共享树 **5 路并行写同一仓库**（含同文件不同域追加，如 sync-engine.ts 被 4 切片先后写入、lark-cli-client.ts 被 5 切片追加）、三轴任务全生命周期（submit/resume/control/wait/accept/cancel/reconcile 查询）、diting 审核任务带 shell 的权限面、provider 网络故障窗口、上下文压缩存活注入。

## 1. 阻塞级问题（发生过一次就损失显著）

### 1.1 accept 响应与持久化状态静默不一致 ⭐ P1
- **现象**（1 次）：P0-S4（7d403656）的 task_control accept 返回 `acceptance=accepted receiptSeq=2`，约 2 小时后主上要求清点非常态任务时，task_query receipt 档显示回执仍为 **seq=1 / acceptance=unreviewed**——验收记录静默缺失（时值 provider 网络故障窗口，疑为该窗口期写入丢失）。损失：依赖「主上主动要求清点」这一偶然事件才发现；若未发现，收口总账将含一条假验收。恢复：凭当前回执重新 accept（1 轮）。
- **根因**：插件层/存储层——控制面响应与契约存储写入之间缺乏一致性保证（响应先行、落盘失败无回滚信号）。
- **改进方案**：① accept 成功路径增加落盘确认（写后回读 revision/stateSeq，不一致则在响应中降级为 warning）；② 或在后续任意 task_query 中检测「accept 声称 seq=N 但存储 seq<N」的会话标记一次告警。成本：低（单点校验）；收益：消灭「假验收」这一最危险状态。
- **责任归属**：插件。

## 2. 摩擦级问题（重复发生、有变通但不顺手）

### 2.1 expert 审核任务的 shell 权限漏声明 → 2 轮往返 + 1 个废任务
- **现象**（1 次，损失 2 轮 + 1 cancel）：diting 收口审核任务书未写 scope.shell（默认 deny）→ 审核者 blocked 报「无 shell 无法取 diff/复跑」→ resume 续接（95a40511）仍无 shell（继承原范围，正确行为）→ 最终新派带 shell 任务（d6b1cde0）完成。
- **根因**：使用者债（任务书漏声明）；但插件有低成本防呆面——审核任务书明确写了「跑测试/git diff」却 shell=deny 的组合可被预检发现。
- **改进方案**：task_submit 预检：任务书含「跑/复跑/vitest/git diff/实测」类动词而 scope.shell 缺省或 deny 时，dryRun/提交响应附一条非阻断提示。成本：低；收益：本会话省 2 轮 + 1 任务。
- **责任归属**：使用者债 + 插件可防呆（降半级 → P2）。

### 2.2 receiptId/waivedCheckIds 手抄易错
- **现象**（1 次，1 轮恢复）：accept 733efb22 时手抄回执 id 一位之差（13968e5e→13998e5e），被 stale-receipt/unknown-id 双重拒绝；repairExamples 直接给出正确值，第二次成功。
- **根因**：使用者债（长 id 不应手抄）；插件 repair 防呆已到位。
- **改进方案**：accept 支持 `receiptId: "latest"`（取该任务当前回执）或「上一次 task_query 返回的 id」引用语义，从源头消灭手抄。
- **责任归属**：使用者债 + 插件可防呆（P2）。

### 2.3 resume 无法扩权时的指引缺失
- **现象**（1 次，1 轮损失）：diting resume 后仍无 shell，错误信息只说「请实际挂载 shell 执行工具后重派」——「重派=新任务」这一正确路径需自行推断（工具说明有写，但错误现场未引用）。
- **改进方案**：resume-failed 响应的 repairExamples 增加一条：「权限/工具面不可经 resume 扩展，请新派 task_submit 并在 scope 中声明」。
- **责任归属**：插件（文档已有、现场指引缺）。

### 2.4 异源暂存警示同批 commit 流内重复 6 次
- **现象**（6 次，零阻断）：分批提交流中每次 git add 均触发全量异源警示（首两轮全文、后折叠），信息正确且有 `AMAGI_STAGED_ORIGIN_HINT=0` 出口，但同会话第 3 次起重复提示的边际信息为零。
- **改进方案**：同会话同批 commit 流内第 3 次起自动折叠为一行计数（保留首次全文与出口提示）。
- **责任归属**：插件（P3）。

### 2.5 bash heredoc 追加无锚点校验（本会话 Agent 自伤）
- **现象**（1 次，2 轮返工）：Leader 用 `cat >>` 向 cloud-history.test.ts 追加测试，引用了不存在的 helper（未先读文件结构）；python 重写时 split 残留又留语法尾巴（L1069 tsc 报错后修复）。
- **根因**：纯使用者债（应先读再写）；edit 工具有 editReference/唯一锚点校验而 bash 追加没有——但为 bash `>>` 做代码级防呆成本高、误报面大。
- **责任归属**：使用者债，插件无低成本防呆面 → **豁免沉淀**（记录在案）。

- **上下文缺失型失败占比**：契约类 2 次（receiptId 手抄、resume 扩权）——均属「正确信息存在于工具文档但不在执行现场」，插件防呆（repair 提示）使平均恢复轮数=1。
- **同类失败第二次发生率**：0（每类失败本会话均只发生一次；accept 丢失类无法二次验证）。
- **平均恢复轮数**：1.4 轮（7 次失败事件/10 轮恢复动作）。

### 3.3 反向观察
- 撞写守卫 3 次全中（共享树 5 路并行的安全性基石）——失败率统计里「被守卫拦截」不算插件失败，算插件成功。
- provider 三连失败但阶梯等待指引 + 完成自动通知使总损失 ≈ 4 分钟等待 + 1 轮重试，恢复体验良好。

## 4. 顺手但可以更好的地方（正向面）

1. **edit-guard 过期 oldText 拦截**：P0-S2 与 P1-S5 并行写 lark-cli-client.ts，后者 edit 被拒后按协议重读再追加，最终零覆盖零丢失——22 切片共享树并行的安全基石（证据：P0-S2 报告 §五撞写记录）。
2. **完成契约校验（无 DONE 标记警示）**：P0-S8 终稿缺 AMAGI:DONE，回执明确「建议核验勿直接采信」，驱动 Leader 亲验 28/28 后才 accept——防假 done 机制真实起效。
3. **stale-receipt + repairExamples**：手抄错 id 一轮自愈（正确值直接给到 repair 示例里）。
4. **压缩存活注入（CONTINUATION_ONCE）**：上下文压缩瞬间保住 3 个进行中任务的目标与清单，一行确认零丢失。
5. **三轴全量查询**：task_query 无 handle 列全部契约任务，使「accept 丢失」这类静默异常可被一次清点发现（配合主上指令）。

**豁免未沉淀（4 条）**：
- provider Connection error 三连：外部网络故障，插件阶梯等待+自动通知恢复良好（正常成本非插件债）；
- heredoc 盲追加 2 轮返工：纯使用者债，无低成本插件防呆面（§2.5）；

- 撞写 3 次：护栏正常工作属正向面（§3.3），非失败。

## 6. 一句话总结

22 切片共享树 5 路并行、33 次验收仅 1 次状态静默缺失且可修复——插件的并行安全基座（edit 守卫/完成契约/三轴状态）已是这类大批量编排的可用底座；剩余差距集中在「控制面响应与存储一致性」与「防呆提示的前移」（审核 shell 预检/receiptId 引用），均为低成本单点改进。
