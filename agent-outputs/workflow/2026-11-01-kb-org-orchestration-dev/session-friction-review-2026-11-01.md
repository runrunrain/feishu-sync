## 1. 阻塞级问题

本会话无阻塞级问题（无假 done、无误杀、无数据丢失）。最接近阻塞的是 fuxi 三连 429（累计损失约 40 分钟），但其根因在 provider 账号配额，插件侧的错误终态、恢复指引、零写入回执均按设计工作，故归入摩擦级。

## 2. 摩擦级问题

### 2.1 provider 账号级 429 限流后，恢复路径全手工 ⭐ P1
- **现象**：fuxi 任务（模型 anthropic/claude-opus-5-5:high）连续 3 轮 429（5f76d8b9 原派 / 7405b877 resume / b800f016 resume，间隔 90s 与 300s 均无效，共 12 次子调用全拒）。损失：3 轮派发 + ~7 分钟空等 + 手动排查。恢复动作：读 `~/.pi/agent/amagi.json` → edit 换 fuxi 模型为 openai-codex/gpt-6-astra:high → 重派成功 → 任务完成后 edit 恢复原配置，全程 4 次手工操作。
- **根因**：插件层——resume 明示「无 model 参数，不承诺同 provider 立即恢复」，重派也无模型覆盖入口；账号级限流的探测（等待多久才值得再试）与切换建议（配置里还有哪些可用角色模型）完全靠 Leader 自查配置文件。
- **改进方案**：① 恢复指引里附「当前配置内可用备选模型清单」（amagi.json agents 各角色模型已可枚举）；② 提供 `task_submit({profile/model 覆盖})` 或临时模型覆盖参数，免去手改全局配置+事后恢复两步；③ 同一任务连续 2 次 provider-quota 类失败后，resume 指引不再建议同 provider 重试（本会话第 3 次尝试由 Leader 自行判断放弃等待）。
- **责任归属**：插件层（恢复指引的信息完整性）。使用者侧无失误。
- **证据锚点**：taskId 5f76d8b9 / 7405b877 / b800f016 三份 error 回执（均 429 request_id 可查）；恢复后 e0bc4d28 done。

### 2.2 任务书验证命令与 shell 授权不匹配，提交后才提示 ⭐ P1（上次复盘 2.1 同构复发）
- **现象**：T1 首派（9c6ee03e）任务书含 `npx tsc --noEmit && npx vitest run` 自验要求，但未申请 `scope.shell=guarded`；提交回执才出现软提示「子进程将无法自验」，被迫 cancel 重派（74d1411b）。损失 1 轮 + 1 个废任务。上一会话（2026-10-28 复盘 §2.1）diting 任务同构问题已发生——**同根因第二次发生**。
- **根因**：插件层——检测逻辑已存在（回执能提示），但校验发生在提交后而非提交前；effects=unknown 的 dispatch 已发出才提示。
- **改进方案**：task_submit 提交前预检：任务书文本含验证执行类关键词（tsc/vitest/npm test/命令自验）且 shell=deny/缺省 → 直接 ContractError 拒单（effects=none）并附 repairExample（加 shell=guarded 或注明「验证: Leader 代跑」）。上次复盘建议同类，本会话证明仅靠回执提示不足以消灭第二次。
- **责任归属**：使用者债（我两次都写漏）+ 插件可防呆（预检拒绝成本极低）——按口径归「插件可防呆」，P1。
- **证据锚点**：9c6ee03e 取消回执（含「任务书含验证执行要求…但子进程未获 shell 通道」提示原文）；上一复盘 §2.1。

### 2.3 contextRefs 传子任务新建文件路径，重复犯错 2 次 ⭐ P2
- **现象**：T2a/T3 并行批派发时把 T1 刚创建的 `server/src/kb/knowledge-schema.ts` 等路径放进 contextRefs → ContractError context-ref-unavailable（effects=none）整批拒单；T4a 派发时**再次**犯同错（同批第二次）。每次 1 轮修复（去 refs 改用 inputs 传递）。
- **根因**：使用者债为主（「子任务产物 ≠ 可继承历史锚点」这条规则学得不牢）+ 插件可防呆：拒绝信息已很清晰（含 repairExamples），但提交前可校验 refs 路径是否存在于「当前可继承历史」并提前提示「该路径不在历史锚点中——若是子任务产物请改用 inputs」。
- **改进方案**：① 提交前 refs 预检+分流建议（同 2.2 的预检通道）；② 或在 contextRefs 参数文档/错误信息中直接列「新建文件请走 inputs」的正例（当前 repairExample 只说去掉）。
- **责任归属**：插件可防呆，P2（第二次发生率 100%，但每轮损失小）。
- **证据锚点**：两次 ContractError（context-ref-unavailable，message 含「不在可继承的当前可见历史中」）。

### 2.4 共享树并行批的兄弟中间态编译干扰 ⭐ P2
- **现象**：T2a∥T3 并行期间，T3 回执披露「期间主树 agent-tool-service.ts 出现兄弟中间态编译错/测试失败，已甄别非我写面，最终态兄弟已自愈」。发生 1 次、自动恢复、未引发错误返工——但风险真实：若 T3 当时的全仓 tsc 失败被误判为自己代码问题，会触发无意义返工（写面不相交但 tsc 是全仓编译，读取面必然看到兄弟半成品）。
- **根因**：协议层——共享树并行是插件支持的默认形态，但「并行批内全仓编译/全量测试会读到兄弟中间态」这一风险没有任何提示；子任务靠自觉甄别。
- **改进方案**：① task_submit 检测到同批（或同时 running）其他任务的写面与本任务 read 面重叠时，在任务注入上下文里提示「共享树存在并行兄弟 X，全仓编译失败先甄别是否兄弟中间态」；② 任务书模板段落（低成本）：并行批派发时 Leader 主动写明——本次已靠 T3 自身素质化解，可作为手册级缓解。
- **责任归属**：插件层（并行上下文注入）+ Leader 手册级兜底。P2（发生 1 次、损失 0，但概率性大损失）。
- **证据锚点**：T3（46784047）回执「需要 Leader 知情」第 ② 条原文。

### 2.5 codemode 沙箱保留名冲突的错误信息不指路 ⭐ P2
- **现象**：首用 codemode 时写 `const tools = await searchTools(...)` → `SyntaxError: invalid redefinition of parameter name at codemode.js:2:13`。错误完全没提「tools 是沙箱全局保留名」，靠猜测试才定位。1 轮恢复，第二次发生率 0。
- **根因**：插件层——沙箱注入的全局名（tools/text/image/console/store/exit）对执行者不可见，错误信息只有 JS 语法层定位。
- **改进方案**：SyntaxError 触发时若冲突标识符在保留名清单内，错误信息追加「`tools` 是 codemode 沙箱全局保留名，请换变量名（保留名清单：tools/text/image/console/store/exit）」。
- **责任归属**：插件可防呆，P2。
- **证据锚点**：`fixture-codemode-reserved-name.md`（本目录，最小复现）。

### 2.6 软提示重复出现无会话内去重（上次复盘 2.4 同构复发）⭐ P3
- **现象**：① 「管道退出码」提示本会话出现 6 次（第 3 次起折叠为 1 行——降级设计好，但前 2 次全文各 ~150 字）；② 「[amagi env] Electron ABI 构建」提示随每次 server 目录 bash 出现 ~5 次（本会话实际从未发生 NODE_MODULE_VERSION 问题）。上次复盘 §2.4 是同构问题（异源暂存警示重复 6 次）。
- **根因**：插件层——软提示按事件触发，无「同类提示本会话已展示 N 次」抑制或条件失效（如 ABI 提示可在该目录测试实际通过后自动失效）。
- **改进方案**：软提示统一加会话级计数：首次全文、第二次起一行折叠（管道退出码已做到，推广到 env 类）；条件型提示（ABI）在触发条件被证伪（同目录测试通过）后本会话不再出现。
- **责任归属**：插件层，P3（纯上下文节省，单次损失小）。
- **证据锚点**：本会话 bash 输出中 6 次「管道退出码」标记（第 1/2/3/4/5/6 次软提示可见）；5 次「[amagi env] Electron ABI」标记。

## 3. 失败深度分析

### 3.1 失败全景统计

| 类别 | 次数 | 典型案例 | 责任归属 |
|---|---|---|---|
| shell 语义陷阱 | 1 | curl 无 --max-time 挂死 60s 超时（bash 诊断提示「前台长命令被中止」辅助定位） | 使用者债，恢复 1 轮 |
| 运行时/模块解析 | 0 | — | — |
| 工具参数误用 | 3 | T1 漏 shell（§2.2）、codemode 保留名（§2.5）、tavily max_results=3（校验信息明确，1 轮） | 2 条插件可防呆 |
| 路径计算错误 | 0 | — | — |
| API/契约试错 | 3 | contextRefs 不可用 ×2（§2.3）、context-too-large ×1（信息优秀） | 1 正常成本 + 2 可防呆 |
| 插件拦截 | 1 | git stash 链命令被守卫拦（正确拦截，见正向 4.3） | 插件正确工作 |

上下文缺失型失败（命令合理但关键信息不在执行者脑内）：3/8 ≈ 37%（shell 授权匹配、refs 历史锚点规则、沙箱保留名）——三者都有「信息在插件内、时机不对」共性，是预检/错误信息增强的可系统消除部分。

### 3.2 逐类改进方案
见 §2 各条改进方案（按 ROI：2.2 预检拒绝 > 2.1 限流恢复信息 > 2.5 错误信息增强 > 2.3 refs 预检）。

### 3.3 反向观察
失败率低（bash ~40+ 次调用、硬失败 2 次 ≈5%；task 契约类拒单 4 次/17 派发 ≈24% 但全部 effects=none 或 1 轮恢复，零副作用泄漏）；所有失败平均恢复 1 轮；同类失败第二次发生率 2/4（shell 授权、refs——恰是两条「插件可防呆」项，佐证预检价值）。

## 4. 顺手但可以更好的地方（正向面）

1. **diting 对抗检验链质量极高**：终审 8 findings 全部带可重跑复现代码（内联 node 取证），增量复审又抓出修复引入的回归 N01 与未关闭 F05-R，且「反向取证」要求（临时降级修复证明测试能抓住原缺陷）被我采纳进 T8 验收——审核产物直接可执行，零来回扯皮。锚点：diting-final-review.md / diting-recheck.md。
2. **error 回执的可 waive 收口**：三次 429 零写入回执，accept 时 missing/可waive 清单直接给出（含 artifact-integrity missing 全列），三次收口各 1 轮完成，账面无残留。
3. **bash 守卫拦截 git stash 链**：拦截理由充分（共享 stash 栈弹错他人条目风险）、明确声明「整条命令未执行、系统状态未变」、给出分步替代——我改走更简单的 grep 验证路径，1 轮恢复且无状态污染。
4. **context-too-large 拒绝信息**：附最大来源字节排序表，一眼看出是会话历史过长所致，改 isolated 重发 1 轮成功——「拒绝即指路」的范例。
5. **run_bg 管理常驻 dev 进程顺畅**：vite/独立端口 server 共 4 个句柄，start（返回日志路径）/result（尾部摘要）/cancel（组级回收）闭环完整；虽然软提示说「watch/dev 型不适用」，但短期存活+超时预算的场景下实际工作良好。
6. **派发回执的产物摘要**：净变化/写面登记命中/diff 统计直接可作验收抽查依据，T4b「登记 12 处→命中 12 处未命中 0」的写面对账让 Leader 抽查成本降到每任务 1-2 条命令。

## 6. 一句话总结

插件在长会话重编排场景的整体身位扎实（0 假 done、验收链完整、守卫与拒绝信息质量高），差距集中在「提交前预检」与「失败恢复指引的信息完整性」两处——四个可防呆点全部是信息已在插件内、只是给晚了一步；补齐预检后，本会话 8 次失败中有 4 次可完全消灭。
