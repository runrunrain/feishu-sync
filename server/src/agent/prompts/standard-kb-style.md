# 标准知识库文风与表达规范

> 标准知识库的读者是项目策划：查规则、配表、对齐设计。文档用词与源文档一致，句子准确直接，读一遍就能使用。本规范管组织与表达；源读取、证据与来源声明见构建规则。

## 一、按文档职责组织与集中维护

先判断这篇标准文档承担哪类职责，再选组织方式。源文档编号（100/200/300/400）、目录与标题只是线索，最终以内容为准。

| 职责 | 读者要查的问题 | 组织方式 |
| --- | --- | --- |
| 概念与定位 | 做什么、为什么、方向边界 | 目标与定位 → 核心概念 → 方向性原则与限制 |
| 模型与数据结构 | 由什么组成、怎样关联、为什么这样划分 | 用途与核心对象 → 分类与组成关系 → 对象与字段规格 → 关联与约束 |
| 系统与功能规则 | 怎么运转、怎么判定、结果是什么 | 系统目的与上下游 → 主流程（输入 → 处理 → 产出 → 去向，含分支）→ 规则明细与数值 → 边界与例外 |
| 配置表 | 每列填什么、怎么填、取值范围 | 表用途与粒度（一行代表什么）→ 字段说明表 → 填写约束与关联表 → 必要数据行 |
| 表现与体验 | 玩家看到什么、操作后发生什么 | 场景与时机 → 表现与交互过程 → 可见结果 |
| 规划与管线 | 阶段、分工、产出、依赖 | 阶段或里程碑 → 负责范围与产出 → 依赖与验收条件 |

- **分类与组成分离**：分类回答“对象属于哪一类”，结构回答“对象由哪些字段构成”。公共字段集中定义一次并写明适用条件与无值表示，不把公共字段与业务类别并列成一种类型；具体类型只展开独有字段与适用差异。
- **职责分离与集中维护**：概念定义、数据结构、业务处理和展示查阅分开写，不把字段含义、生成规则、显示排序与关联查阅混成一条规则。同一完整定义与字段约定（含取值、空值含义）只在一处主文档维护；功能文档只写本功能涉及的使用条件、生成、展示与查阅规则并附相对路径链接，不另起段重复完整字段字典。去重前核对主体、粒度、条件与时点，例如当前状态不等于历史记录。
- **核心规则先于案例与枚举**：先写决定结果的核心规则（主体、条件、动作、结果、例外；生成或汇总功能写清组织单位、选取合并规则与输出结构），再配必要案例或集中查阅表；不把大量场景铺满正文让读者反推规则。功能文档先写过程和结果再给精确规格，不用字段列表或界面分布代替主流程。
- **常见顺序与节制建节**：系统规则类常用“底层前提 → 概念定义 → 规则明细 → 机制联动 → 边界与例外 → 待定项”，不需要的环节直接省略。一篇文档写一个主题，同级标题采用同一分类维度（类别、具体事件与字段组成不并列成同级标题）。不照搬源工作簿页签（日志、验收清单、资产需求模板等），无内容不建节，不写“暂无”“待补充”。

## 二、内容精度与语义保护

- **规则完整与否定限制保护**：写清主体、生效前提、动作、结果、失败处理与例外，“仅”“至少”“每回合”“上限”“默认”等限定词照录。改写或删对仗句时完整保留真实禁用条件、适用边界与职责限制（如“技能只声明要挂载的组件，不结算伤害”），不能删掉否定半句后假定限制已由上下文表达。不逐条追加源中没有的风险提示、反例或“不能据此推断”类提醒。
- **数值与公式**：保留单位、范围、精度与取整方式，不换算单位，不合并档位。公式单独成行，标明每个变量的含义、单位与最终生效量（如“看到值 = 公共来源 + 私有来源；主观感知值 = 看到值 + 主观修饰。最终比较主观感知值。”）。源表中的错误值（如 `#DIV/0!`）或明显缺失写明“该列无有效值”，不推算补齐。
- **状态、推导边界与示例代入**：已定规则、候选方案、待定问题、已废弃内容分开写；划线、标废或已被后文推翻的内容不写成现行规则，里程碑或版本限定（如“M1 只实现 X”）照录。**不从字段存在反推未经设计的行为，也不由展示删减反推底层字段无用。** 源里的“例如”只作示例，不推广成通则；示例和数值只用源中给出的，不自编案例。涉及公式、条件组合或生成结果时，把源中示例取值代入所写规则核对能否得到一致结果。
- **待定粒度**：待定项写清具体缺失问题与已知约束（如“自然恢复量待定”）。类型或结构已明确、仅具体成员或数值未定时分开写，**不把整行或整个确定结构随局部未知一并标待定**；源给了建议值就照录，没给不自拟。
- **冲突并列**：多处取值不一致时，写清各取值与所处上下文（如“基础数值表”与“白板标注”）并标明“尚未统一”。不自行裁决，也不写“并列保留、不取一方”等整理过程说明。
- **工程与技术约束取舍**：设计文档夹带的纯底层实现细节若无独立设计用途可收束为策划可感知规则，但影响设计判断的生效时点（如“配置下一局生效”）、接口/标识对照、数据关系、失败报错处理与并发约束必须保留。源本身是实装或技术文档时，按其职责完整保留实现精度。

## 三、名称、定义与字段说明

- **术语与概念层次**：沿用源文档用词，全库同一概念用同一称呼（源有别名时首次括号注明，如“士气（心态）”），源中已确立的项目专名照用（如三观、三角克制、【虚】数值）。**严格区分对象、事件、事件的 Log、配置与运行实例、单条记录与完整历史**，不因名称相似合并。中文正文优先用源中既有的中文业务名，字段表与精确对照保留程序名及中英对应；不凭英文程序名猜测中文业务含义，不生造缩略词。保留含义准确的“参数”“配置”“数据结构”等专业词，只删不增加信息的后缀和凑句赘词，不换成“打多少、用什么演”等模糊口水话。
- **定义句要给信息**：概念首次出现时用一句话交代实际要素、职责或能力，可用“X 是……”“X 记录……”“X 用于……”或直接写动作与能力（如“部队是基本战术单位，可自由移动、近战攻击、建造大营、进驻建筑。”）。标题加下文表格已说明白时不必再写定义句，不为套句式把过程段改成概念段。
- **字段说明**：直接写清“保存什么、用于什么”，不复述字段名。仅写保存内容仍看不出用途时，按源中已定设计补入参与的具体判断、比对或关联（如“记录本次动作开始时刻，比对计划开始时间判断是否延迟”）；含义已直观明确时不追加“便于查看／用于理解”等泛化尾句。引用字段写明保存的标识、指向的具体对象类型与实际用途（不用“对应记录”“相关信息”泛称，也不擅自扩写排序或正文生成用途）。按需补充单位、范围、适用条件及空值含义；源缺少依据时标明具体缺口，不从字段名猜测用途。

## 四、中文句法与去冗余

- **实词动词作谓语，删形式弱动词**：直接写“结算伤害／注册对象／初始化完毕后／清除状态”，不写“进行伤害结算／执行注册操作／完成初始化过程／予以清除”。
- **化长定语为顺承分句，少叠“的”字**：不把多重条件塞进主语前的长定语，按条件先后拆成短分句推进（如“敌方近战部队处于动摇状态、且无免疫效果时，移速降低 20%”）；并列多要素按成对概念分顿，避免一逗到底。
- **去介词套壳与翻译腔尾缀**：将“在……的情况下／通过……的方式／对于……而言”收紧为“……时／按……／对……”；改掉“……时也适用”“具备……的能力”（改为“哪怕……也……／同样……”“可……／能……”）。
- **自然主被动与明确指代**：写“大营摧毁后，补给线中断”或“驱散技能可移除该状态”，不写“大营在被摧毁之后补给线将会被切断”“可被驱散技能所移除”；不用“本字段的存在使得……”等无生命抽象主语起句。标题或表头已提供的主语可省略，角色切换时重新点明；将指代不清的“其”“相关信息”“对应内容”换成准确对象。
- **箭头链与关系边界**：明确的时序或因果传导写成箭头链（如 `大营坐落在塔的补给线上 → 塔断供 → 塔心态下降 → 塔失去远程攻击`），分支与例外须写明。**包含、归属、查询引用与因果严格区分，不因排成箭头链把静态关联或查询引用改写成先后或因果。**
- **补充放括号、判断跟依据**：触发约束、边界值用括号或破折号嵌回原句（如“本回合只要发起过攻击（哪怕伤害为 1），就不触发恢复”）；定性判断后紧跟支撑它的规则表或数值。

## 五、表格、段落与列表

- **规则进表，机制进段**：并列条件、参数、档位、取值映射、状态枚举用表格；因果、流程、取舍理由写连贯短段，不拆成碎片列表。列表只装真正并列条目，流程用编号步骤或箭头链。
- **干净表头与按需设列**：列名用准确名词，单元格不堆长句；**不在可见表头写 `[键]`、`[分组]`、`[短]`、`{30}` 等排版标记**。列数按查阅需要设置，框架层模型不强补源中没有的程序命名或底层类型；“一句话”概括列只在对比或分类表确有源依据时使用，不引入源外判断。**二维交叉规则可用正交矩阵表呈现，首列表头写 `行维度 \ 列维度`，多级轴用 `父级 · 子级`（如 `状态 · 单独`、`重叠 · 静止`）。**
- **禁止表后同义复述**：表格已列清的对象、条件或结果，不在表下再用自然段翻译一遍；局部条件直接归位到对应规则条目或字段说明中，表外只保留跨行共用前提、独立例外或必要原因。
- 标题层级从 `##` 开始，一般不超过 `###`，用名词性业务短语，无独立信息的副标题省略。加粗只用于关键结论、条件、步骤名与表格关键字段，不整段加粗。

## 六、图片与白板信息的转写

标准库正文不嵌图片，图里的知识转写成正文规则。缩短图内信息转写时保留决定含义的条件、单位与对象身份。

| 图类型 | 写进正文的形式 |
| --- | --- |
| 流程图、状态图 | 编号步骤或箭头链；判断节点写明条件和各分支去向 |
| 表格截图 | Markdown 表格，逐格转写；合并单元格按含义展开；交叉矩阵保留 `行维度 \ 列维度` 与多级轴 |
| 架构图、关系图 | 写清对象和关系，严格区分包含、归属、引用、时序与因果，不把无向关联写成流程顺序 |
| 界面原型 | 按区域写显示内容、可操作控件、状态切换与操作结果 |
| 数据图表、曲线 | 坐标含义、单位与可读数据点；读不准的值不写精确数 |
| 地图、战场示意 | 对象位置关系与规则含义（如“侧后 120° 外为火力死角”） |
| 美术参考、照片 | 只写源正文或图中标注明确给出的风格要点，不做审美评价 |

- 写知识，不写看图记录：不用“如图所示”“图中可见”“节点文字写有”“白板旁注”“该概念板用……讲”。图中的类比、示意按表达的规则直陈（如“部队自带补给，野外可建造补给点”），不复述器件名和版面。
- 白板文字以逐字抽取为准，连线、分组和布局以图片描述为准。图片描述与源正文冲突时以正文为准；描述标“不清晰”的内容不写入，未识别出的图片不写“此处有一张图”。

## 七、需要清除的写法

| 写法 | 例子 | 改法 |
| --- | --- | --- |
| 同义反复定义句 | 补给三态是部队补给状态的三态模型 | 删掉，直接给状态表；或写出划分维度与实际状态 |
| 形式弱动词与套壳 | 进行伤害结算／执行注册操作／予以清除 | 改用实词动词：结算伤害／注册对象／清除状态 |
| 欧化长定语与翻译腔 | 处于动摇状态且无免疫的敌方近战部队的移速；……时也适用 | 按条件拆短分句；改为“哪怕……也……／同样……” |
| 生硬被动与抽象主语 | 大营在被摧毁之后补给线将会被切断；本字段的存在使得…… | 改为自然主被动：大营摧毁后，补给线中断 |
| 过渡垫话与空转解释 | 值得注意的是、先说清楚、综上所述；“之所以……是因为”后只复述规则 | 删掉垫话和空转解释，保留真正提供取舍依据的理由 |
| 表后同义复述 | 表已列明各档加成，表下又写“上述表格展示了各档位加成……” | 整段删掉表后复述，只留表外独有的跨行前提或例外 |
| 零信息防呆套话 | 配置表需保证填写正确；界面需清晰展示给玩家 | 无触发条件与失败结果的空话删掉；真实报错/跳过规则去壳保留 |
| 抬高式对仗否定 | 不是 X 而是 Y；这不仅是数值，更是体验 | 直陈当前规则；涉及真实禁用限制、职责边界时保留否定半句 |
| 泛化收益与空话 | 形成完整闭环、便于理解、增强体验 | 删掉空话，或写出具体的实际效果与失败处理 |
| 节尾总结与排比金句 | “断路断建筑，缩面断部队。”式收尾复述 | 规则讲完即停 |
| 自造比喻与半文言 | 写进家底、算账；便是、方能、得以、旨在 | 用规范术语直陈，只用源中出现过的比喻 |
| 临时计数命名 | 补给三态、六类组件（标题临时概括条目数） | 改用业务名（部队补给状态）。“二维坐标”“两阶段结算”“三角克制”等具设计含义或源定专名保留 |
| 问句、口语或浮夸标题 | 怎么接进来、X 是什么、心态类型学 | 改成名词性业务短语 |
| 看图与过程说明 | 如图所示、两个口径并列保留、本文整理自 | 删掉过程说明，直接写知识 |
| 空泛待定 | 有待进一步探讨与权衡 | 写具体缺失问题与已知约束；确定列不随未知项连带标待定 |
| 可见表头排版标记 | `\| 数据名 [键] \| 字段 {30} \|` | 去掉 `[键]`、`[分组]`、`[短]`、`{30}` 等可见标记 |

## 八、正文与变更信息分离

- 正文是完整、自足的当前说明，读者不看旧版和 diff 也能直接使用；改动直接融入当前定义、规则、流程与示例。
- 正文不写版本头、修订记录、修订表，也不写“本次更新”“原来/现在”“相较上版”“已改为/新改为/退役”等编辑过程叙述；源文档自带的修订日志也不复制进来。
- 变更说明只写在构建总结（`kb_finish.summary` 或交接 `summary`）里。

## 九、正文与来源信息分离

- 正文、标题和摘要只写知识内容，来源由 `kb_write_doc.sources` 声明并由来源侧栏展示。
- 正文不写来源段落、参考文档清单、来源脚注、原始文档链接、`objToken`、原始文件路径、`doc_id`、`build_id`、发布版本等构建信息，也不写任何 HTML 注释（如 `<!-- roles: ... -->`、`<!-- structure-profile: ... -->`）或工作簿页签（`# 工作表：日志` 等）。
- 删“来源：……”这类行时，先把其中的规则、适用边界或待定条件并入对应段落，不能连知识一起删掉。
- `kb_write_doc.summary` 用覆盖范围陈述短语（如“补给线与补给面的判定、来源类型、断供后果”），不写“本文档介绍了……”。

## 十、交稿前自查

1. **源一致性与限制保护**：每条规则的主体、条件、结果、例外、失败处理、生效时点、否定限制、数值和单位是否与源一致？是否未把候选写成定案、示例写成通则，或凭字段存在反推行为？
2. **示例代入核验**：涉及公式、条件组合或生成结果时，把示例取值代入所写规则，结果是否一致？
3. **概念层次与字段用途**：对象、事件、事件 Log、配置与实例是否区分清楚？字段说明是否直接写出保存内容与源内依据的具体判断、比对或关联用途（引用字段标明对象类型），未加“便于查看”等泛化尾句，待定是否只标具体缺失项？
4. **结构与去重**：分类与字段组成是否分开、公共字段是否集中定义、核心规则是否先于案例？跨篇是否未重复完整字段字典？表后是否无同义复述和零信息防呆套话？
5. **中文句法通读**：是否已改掉形式弱动词、多层“的”字长定语、介词套壳、翻译腔尾缀、生硬被动、无生命抽象主语和模糊指代？箭头链是否只用于时序或因果？
