# 标准知识库文风与表达规范

> 标准知识库的读者是项目策划：查规则、配表、对齐设计。文档要让他读一遍就能准确使用，用词与项目源文档一致，句子干脆。本规范管表达；源读取、证据与来源声明见构建规则。

## 一、按文档职责组织

先判断这篇标准文档承担哪类职责，再选组织方式。源文档的编号（100/200/300/400）、目录与标题是判断线索，最终以内容为准。

| 职责 | 读者要查的问题 | 组织方式 |
| --- | --- | --- |
| 概念与定位 | 做什么、为什么、方向边界 | 目标与定位 → 核心概念 → 方向性原则与限制 |
| 模型与数据结构 | 由什么组成、怎样关联、为什么这样划分 | 组成与归属关系 → 对象定义 → 字段表 → 关联与约束 |
| 系统与功能规则 | 怎么运转、怎么判定、结果是什么 | 系统目的与上下游 → 主流程（输入 → 处理 → 产出 → 去向，含分支）→ 规则明细与数值 → 边界与例外 |
| 配置表 | 每列填什么、怎么填、取值范围 | 表用途与粒度（一行代表什么）→ 字段说明表 → 填写约束与关联表 → 必要的数据行 |
| 表现与体验 | 玩家看到什么、操作后发生什么 | 场景与时机 → 表现与交互过程 → 可见结果 |
| 规划与管线 | 阶段、分工、产出、依赖 | 阶段或里程碑 → 负责范围与产出 → 依赖与验收条件 |

- 系统规则类常用顺序：底层前提（不可更改项）→ 概念定义 → 规则明细 → 机制联动 → 边界与例外 → 待定项。这是常见顺序，内容不需要的环节直接省略，不为凑结构补空节。
- 功能类先写过程和结果，再给精确规格；只罗列字段或页面分布，不能代替主流程。
- 一篇文档一个主题。同一规则只在一处完整定义，其他文档用相对路径链接，或只保留理解当前内容所需的最少语境。
- 不照搬源文档的工作簿页签（日志、验收清单、资产需求模板等）。没有内容的槽位不建节，也不写"暂无""待补充"。

## 二、内容精度

标准库要求表达精准，不追求篇幅。写之前先确认每条规则的主体、条件、结果与例外。

- 规则完整：保留生效前提、作用对象、结果和例外。有条件的规则不写成无条件；"仅""至少""每回合""上限""默认"等限定词照录。
- 数值照录：保留单位、范围、精度和取整方式。不换算单位，不自行合并档位。写公式时说明每个变量的含义与单位，再写算出来的量用在哪里。
- 源表中的错误值（如 #DIV/0!）或明显缺失照实写成"该列无有效值"，不推算补齐。
- 状态分清：已定规则、候选方案、待定问题、已废弃内容分开写。源中划线、标注废弃或已被后文推翻的内容不写成现行规则；候选写明是候选；里程碑或版本限定（如"M1 只实现 X"）照录。
- 示例不扩大：源里的"例如"只作示例，不推广成通则。示例、案例和数值只用源中给出的，不自编案例。
- 待定项写成"具体问题 + 已知约束"。源中给了建议值就写上，没给就不自拟。
- 冲突并列：多处取值不一致时，写清每种取值及其所处上下文（如"基础数值表"与"白板标注"），并写明"尚未统一"。不裁决，也不写"并列保留、不取一方"这类整理过程的说明。
- 工程内容：设计文档里夹带的程序实现说明（类名、接口、进程、存储）只保留策划可感知的规则含义，如"改完配置下一局生效"。源本身是实装或技术文档时，按它的职责完整保留。

## 三、句子与用词

**定义句要给信息。** 概念第一次出现时，用一句话交代它是什么、包含哪些要素、负责什么。

- 定义句必须带新信息。"补给三态是部队补给状态的三态模型"只是把标题换个说法，应删掉或改成实义定义：部队补给状态按是否在补给面内、离开多久分为范围内供给、范围外宽限、范围外消耗。
- 标题已经说明白、下文表格直接给出要素时，不必再写定义句。不要每节都套"X 是 Y"开头。
- 用策划专业词，句子用动词推进。有两种偏差都要避免：一是含糊口水话，比如"打多少、用什么演"；二是公文后缀堆砌，比如"……的数据结构，包含……参数、……配置"。好的写法如：伤害包记录一次伤害的完整数据：攻防双方、伤害值、分段与结算步长、受击表现。逻辑层算完生成伤害包，扣血结算和受击演出都直接读它。

**因果用箭头链。** 一条机制传导写成一行：大营坐落在塔的补给线上 → 塔断供 → 塔心态下降 → 塔失去远程攻击。

**判断要有依据。** 可以直接下定性判断，判断后面紧跟支撑它的规则表或数值。

**补充放括号。** 触发约束、边界值、防呆理由用括号或破折号补在原句里：只要每回合都有攻击行为（哪怕伤害为 1），不触发恢复。

**术语以源为准。**

- 沿用源文档用词，全库同一概念用同一个名字。源中有别名时，首次出现写"士气（心态）"。
- 源中已确立的项目专名照用，如三观、三角克制、【虚】数值。
- 不造词，也不为了简短硬缩略。拿不准的词用完整说法。
- 正文叙述优先用中文业务名。字段说明表保留"英文命名 + 中文说明"的格式。

## 四、表格、段落与列表

- 规则进表，机制进段。并列条件、参数、档位、取值映射、状态枚举用表格；因果、流程、取舍理由用连贯短段，不拆成碎片列表。
- 表格列按查阅需要设置：字段表用"字段 | 含义 | 取值/单位 | 示例"，对比表用"优势 | 短板"，映射表写"输入 | 结果"。列名用名词，单元格不写长句。
- "一句话"列只在对比或分类表中使用，前提是每行的定位确实需要概括，且概括能在源中找到依据，比如"大营不打架，只是站对了地方"。参数表、状态表、速查表、字段表都不加这一列。概括不得引入源中没有的判断。
- 列表只装真正并列的条目；流程用编号步骤或箭头链。
- 标题层级从 `##` 开始，一般不超过 `###`。标题用名词性业务短语，直接点明对象，如"补给线判定""大营心态归属"。
- 加粗只用于表格字段名、步骤名和关键结论句，普通段落不加粗。
- 公式单独成行，后面跟一句说明最终生效的量："看到值 = 公共来源 + 私有来源；主观感知值 = 看到值 + 主观修饰。最终比较主观感知值。"

## 五、图片与白板信息的转写

标准库正文不嵌图片。图里的知识要转写成正文，写成读者不看图也能直接使用的规则。

| 图类型 | 写进正文的形式 |
| --- | --- |
| 流程图、状态图 | 编号步骤或箭头链；判断节点写明条件和各分支去向 |
| 表格截图 | Markdown 表格，逐格转写；合并单元格按含义展开 |
| 架构图、关系图 | 写清对象和关系，区分包含、引用、时序、因果 |
| 界面原型 | 按区域写显示内容、可操作控件、状态切换与操作结果 |
| 数据图表、曲线 | 坐标含义、单位与可读数据点；读不准的值不写精确数 |
| 地图、战场示意 | 对象位置关系与规则含义（如"侧后 120° 外为火力死角"） |
| 美术参考、照片 | 只写源正文或图中标注明确给出的风格要点，不做审美评价 |

- 写的是知识，不是看图记录。不写"如图所示""图中可见""节点文字写有""白板旁注""该概念板用……讲"。图中的类比、示意按它表达的规则写，比如"部队自带补给，野外可建造补给点"，不复述器件名和版面。
- 白板的文字以逐字抽取为准，连线、分组和布局以图片描述为准。
- 图片描述是机器转写。与源正文冲突时以正文为准；描述中标"不清晰"的内容不写入。未能识别的图片，正文只写源正文给出的信息，不提"此处有一张图"。

## 六、需要清除的写法

以下写法在团队文档中不出现，命中即改：

| 写法 | 例子 | 改法 |
| --- | --- | --- |
| 同义反复的定义句 | 克制三方是定位迥异的三类单位 | 删掉，直接给面板表；或写出实际要素 |
| 对仗否定句 | 不是 X 而是 Y；X 而非 Y | 直接写 Y。单边禁令（"不产生独立 debuff"）保留；源原句保留 |
| 口播引导与叙事者出场 | 接下来、值得注意的是、一句话概括、先说清楚、什么意思呢、换句话说、综上所述 | 删去引导壳，看后文是否直接成立，成立就删 |
| 节尾总结与排比金句 | "断路断建筑，缩面断部队。"式的收尾复述 | 规则讲完即停 |
| 抽象拔高 | 这不仅是数值，更是体验 | 写具体机制与操作反馈，否则删 |
| 自造比喻与代称 | 写进家底、算账、围着它转 | 用规范术语直陈。只用源中出现过的比喻 |
| 半文言虚词 | 便是、方能、得以、旨在、就此 | 换成平实说法 |
| 计数锚定命名 | 两层补给模型、补给三态、六类组件 | 标题和命名用业务名（补给线与补给面、部队补给状态）。正文"分为三种"和源中已确立的专名不受限 |
| 问句或口语标题 | 怎么接进来、X 是什么、先钉地基 | 改成名词性业务短语 |
| 生造或浮夸标题 | 心态类型学 | 改成"各实体的心态含义" |
| 整理过程说明 | 两个口径并列保留、本文整理自、以下按源顺序 | 删掉，直接写知识 |
| 空泛待定 | 有待进一步探讨与权衡 | 写具体问题与已知约束 |

## 七、正文与变更信息分离

- 正文是完整、自足的当前说明，读者不需要知道旧版、也不需要看 diff 就能理解。
- diff 只是更新的输入，不能原样进入正文。改动要融入定义、规则、流程与示例，直接写当前结论。
- 正文中不写以下内容：版本头、变更或修订记录、修订表；"本次更新""原来/现在""相较上版""已改为/新改为/退役"一类编辑过程叙述。源文档自带的修订日志也不复制进来。
- 变更说明只写在 kb_finish.summary 里。系统有独立的变更入口展示源差异、标准文档差异和版本说明。

## 八、正文与来源信息分离

- 正文、标题和摘要只写知识内容。来源由来源侧栏展示，只通过 kb_write_doc.sources 声明。
- 正文中不写以下内容：来源段落、参考文档清单、来源脚注、原始文档链接；objToken、源标识、原始文件路径、doc_id、build_id、发布版本等构建信息。
- 删"来源：……"这类行时，先把其中的规则或边界条件融入对应段落，不能连知识一起删。例如"格挡的具体减免数值尚未明确"要保留在格挡规则中。
- kb_write_doc.summary 写覆盖范围，用陈述短语，如"补给线与补给面的判定、来源类型、断供后果"。不写"本文档介绍了……"。

## 九、交稿前自查

1. 每条规则的条件、结果、例外、数值、单位都与源一致吗？有没有把候选写成定案、把示例写成通则？
2. 每个定义句都带了新信息吗？删掉之后，标题加表格是否已经说清？
3. 表格里有没有只复述其他列的"一句话"列，或者源中没有的判断？
4. 通读标题：有没有问句、口语、计数锚定、生造词？
5. 有没有"如图所示"、看图记录、整理过程说明、节尾总结？
6. 写这篇文档的目标：一个没读过源文档的策划同事，读完能直接据此配表、实现或对齐设计。
