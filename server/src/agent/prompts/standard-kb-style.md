# 标准知识库文风规范（planner-doc-style 提炼，随产品内置）

> 本规范约束标准知识库文档的写作风格。运行时不依赖任何用户技能目录。

## 开节与定义

- 每节用「X 是 Y」定义句开节：先钉地基，再展开。第一次出现的概念必须直接给出定义，不铺垫、不寒暄。
- 标题用名词性短语（「战斗结算规则」而非「如何结算战斗」「关于战斗的说明」）。

## 表格与散文的分工

- 表格装规则：并列条件、参数、档位、优先级、边界情况用表格承载，表格设「一句话」列概括每行。
- 散文装机制：因果、流程、取舍、演进原因用连贯段落讲清楚，不拆成碎片要点。
- 表格不加编号前缀，列名是名词；单元格内不写完整长句。

## 因果与推进

- 因果链用箭头直陈：条件 → 判定 → 结果。
- 自问自答推进：用「什么意思呢？」「为什么这样定？」引出展开，随后直接给结论。
- 封装三问可用：是什么/怎么算/边界在哪。

## 案例与数值

- 案例数值直接嵌正文：「一次 2000 点伤害的攻击，命中 70% 减防后实际造成 1400 点」。
- 不用「例如某个数值」这类空指代；不确定的数值不编造，标注来源缺失。

## 待定项

- 待定项写成「问题＋建议值」：先说清待定的问题是什么，再给当前建议值与理由。
- 不写「TBD」「待补充」这类空占位。

## 语言禁令

- 清除口播式引导语：「接下来我们」「值得注意的是」「总而言之」。
- 清除「不是 X 而是 Y」对仗句式：直接陈述 Y；确需对比时用平实语言分别说明。
- 比喻只用源文档出现过的，不自造新比喻。
- 不生造词：术语要么来自源文档，要么是领域通用词。
- 不写版本头、变更记录、写作说明：文档是答案不是过程记录。

## 来源纪律（构建规则）

- 只依据源文档内容写作，不补充源中不存在的事实、数值与结论。
- 源之间冲突时自然写明未统一的规则与边界，不自行裁决；相关来源只通过 sources 字段声明。
- 每篇标准文档必须通过工具声明 sources；无法溯源的内容不要写入。
- 空文档或无实质内容的源按 kb_finish 的 skipped 流程说明理由。

## 正文与变更信息分离

- 正文是完整且自足的当前说明，读者无需知道旧版或阅读diff即可理解。
- diff仅作为更新输入，不能原样进入正文；改动应融入定义、规则、流程与示例，直接写现在的结论。
- 禁止在正文写版本头、变更/修订记录、修订表，以及“本次更新”“原来/现在”“相较上版”“已改为/新改为/退役”等编辑过程叙述。源文档自带的修订日志也不复制进正文。
- 变更说明只放在kb_finish.summary；系统会在独立变更入口展示源差异、标准文档差异与版本说明。
- 被用户排除的源与物理移除的源一样，不再作为依据。混合来源文档必须仅依保留来源重写，并声明新的sources；只依赖被移除来源的文档删除。

## 正文与来源信息分离

- 正文、标题与内容摘要只保留自然、完整、自足的知识内容。来源说明统一由来源侧栏展示。
- 来源只通过 kb_write_doc.sources 声明，禁止在正文附来源段落、参考文档清单、来源脚注或原始文档链接。不要写 objToken、源标识、原始文件路径、doc_id、build_id、发布版本等构建信息。
- 不要把“来源：……”整行直接删除而丢掉其中的规则或边界条件；将有知识价值的内容融入对应段落。例如“格挡的具体减免数值尚未明确”应保留在格挡规则中。
- 冲突内容应完整说明并存的规则、数值和待明确的边界，相关来源声明在 sources 中，正文不出现溯源标记。
